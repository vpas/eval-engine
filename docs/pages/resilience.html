How it works

Resilience & high availability

Resilience is split into two layers that are engineered separately. The data-correctness layer (does a crash ever lose or double-count a result?) is the strongest part of the system — built into the execution protocol itself. The availability layer (does a pod or connection blip cause an outage?) is handled by replicas, HA stores, and connection robustness, with one deliberately-accepted ceiling.

Layer 1 — correctness under failure

The execution plane is resilient by construction, because the ledger is the single source of truth and every step is idempotent on re-entry (full detail on the Execution page). The guarantees:

GuaranteeMechanism
No completed sample is lost Ack-before-flip: a ledger row flips done only after ClickHouse durably acks the result.
No result double-counted ReplacingMergeTree dedups re-executions; headline metrics computed once at finalize.
Dead workers self-heal Lease expiry reclaims a crashed worker's running tasks; long batches renew via a heartbeat thread.
Poison samples don't block Retry-with-backoff + not_before gating; bounded attempts then terminal failed.
Idempotent finalize Keyed on the run's authoritative total; a crash mid-finalize re-runs no-ops.
Runaway runs are capped Per-request model timeout, per-sample wall-clock limit, and a budget sweep.
Clean rollouts Workers graceful-drain on SIGTERM; the orchestrator hands over leadership in ~1s.
The key property A wrongful reclaim, a spot eviction, a worker OOM, or a whole-cluster restart is wasted compute, never corruption — because idempotent ClickHouse writes + the ephemeral ledger mean recovery is always "re-derive from the ledger." There is no run-level memory state to lose.

Layer 2a — connection robustness

The highest-value, cheapest availability fix. A database connection dropped underneath the process (a Neon failover or cold-start, an idle reaper, a NAT timeout) is not flagged closed — it raises on the next statement. Without a retry, that crashes a worker or orchestrator loop. So the storage tier wraps every call:

  • Postgres — a bounded shared psycopg_pool liveness-checks a connection on checkout (a dead socket is replaced before the query), and a _run() helper retries the rarer mid-statement drop with bounded backoff. Autocommit singletons make retry safe; idempotent ledger writes make a lost-ack double-apply benign.
  • ClickHouse — a mirror _run() drops and rebuilds the client on a connection error and retries. This matters doubly because the ack-before-flip commit inserts to ClickHouse before flipping the ledger, so a CH blip would otherwise stall execution, not just reads. The retried insert is safe: ReplacingMergeTree collapses an identical re-insert.

The effect: transient infra hiccups become silent recoveries instead of crash-loops.

Layer 2b — leader election & the split-brain it exposed

The orchestrator (and training monitor) run ≥2 replicas for a warm standby but only the leader ticks. Leadership is a Postgres session-scoped advisory lock:

  • Acquire via pg_try_advisory_lock on a dedicated connection held for the process lifetime (released automatically if the process dies).
  • Graceful handover — a SIGTERM handler explicitly pg_advisory_unlocks, so a rollout hands leadership over in ~1s rather than waiting out a lock TTL.
  • Ungraceful death (SIGKILL/OOM/node loss) — the standby loop reaps a stale lock: a live leader refreshes its lock connection every tick, so an idle-past-threshold holder is a safe "crashed" signal to terminate. Worst-case admit/finalize pause ≈ the 20s reap window + a 5s standby poll — and in-flight workers keep going without the orchestrator, so it's a brief scheduling pause, not an outage.
The pooled-endpoint gotcha At 2 replicas, both pods initially logged as leader — split-brain. Root cause: the app's transaction-pooling (PgBouncer / Neon -pooler) endpoint doesn't preserve the backend session that a session-scoped advisory lock relies on, so every replica "acquired" it. The fix: the leader connection alone uses a session-mode endpoint (_leader_dsn()), while the rest of the app keeps the pooled endpoint. A correctness requirement the moment you run more than one replica.

Layer 2c — HA for the stateful backends

StoreHA topologyBehavior on a node/pod loss
ClickHouse 3-replica StatefulSet, ReplicatedReplacingMergeTree ON CLUSTER, embedded ClickHouse Keeper (3-node raft quorum), pod anti-affinity. Every replica holds a copy; reads survive deleting a replica via the load-balanced Service. Verified in-cluster (active_replicas=3, failover read survived).
Redis 3-pod StatefulSet (1 master + 2 replicas) + a Sentinel sidecar each (quorum 2), anti-affinity. Sentinel promotes a replica on master loss; the old master rejoins as a replica. Verified automatic failover.
Object store One regional bucket (GCS is itself regionally redundant + highly available). Acceptable as-is; transcript writes are sampled and off the correctness path.
Postgres Managed Neon (its own storage durability + failover), reached resiliently (above). A failover/cold-start is ridden out by the retry wrapper.

Layer 2d — control/edge replicas & disruption budgets

The control and edge tier is stateless, so HA there costs only a second small pod. All singletons were bumped and protected:

  • replicas: 2 for the API, orchestrator, frontend, and oauth2-proxy (the front gate whose loss would make the whole surface unreachable).
  • PodDisruptionBudgets (minAvailable: 1) so a node drain/upgrade can't evict the sole replica of a singleton; minAvailable: 2 for the 3× ClickHouse/Redis StatefulSets to preserve quorum.
  • Topology spread across hostnames for the stateless pods.
  • KEDA operator replicaCount: 2 (it leader-elects internally) so the autoscaler isn't a single point of freeze.
  • Gateway resilience — allowed_fails: 3 + a cooldown so one bad upstream doesn't down the whole model deployment; workers' per-request timeout means a hung call can't wedge a worker.

SPOF inventory & the accepted ceiling

Everything funnels through Postgres — it is the ledger, the run metadata, the leader lock, the KEDA scale signal, and the heartbeat table, so it's the one component whose loss touches all four roles at once. That's why connection robustness (above) is the headline fix. The remaining posture:

ComponentStatusNote
GCP zoneAccepted ceiling (POC)Single zone — a zonal outage is a total outage. A deliberate cost trade (free zonal control plane, ~⅓ the always-on node cost).
Postgres / NeonMitigatedUniversal coordinator; retry wrapper + Neon's own failover. A pg_connections alert is deferred (fine at POC scale).
Control/edge singletonsFixedreplicas: 2 + PDBs everywhere.
ClickHouse on the commit pathMitigatedHA cluster + the insert retry; a full decouple (load CH async off the hot path) is a considered future design change.
Worker pool (spot-only)AcceptedMass eviction is a throughput dip, not data loss (lease reclaim preserves correctness). An on-demand fallback was evaluated and dropped.
Single-zone, deliberately For the proof-of-concept, single-zone is an accepted, documented ceiling — not an accident. The lift-it-later path is a named Terraform toggle (regional_ha=true: regional cluster + node pools + zone topology spread), roughly 3× the always-on cost, triggered when the platform takes on an availability SLO. Until then, the work targets failures that happen within a healthy zone — node drains, pod crashes, a Neon blip — which are frequent and cheap to survive.
