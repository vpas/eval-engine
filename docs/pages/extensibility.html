Foundations

Extensibility, security & operations

The last set of foundations: how to add capabilities without touching the core, how untrusted model-generated code is contained, how the platform is observed in production, and the vNext training-monitor track built entirely by reusing the existing machinery.

Extensibility — the plugin contract

The orthogonality of model ⟂ harness ⟂ scorer ⟂ dataset is enforced by four independent plugin kinds, composed only at RunSpec resolution. Adding an eval capability is shipping a plugin — with zero core changes.

KindWraps (Inspect)ReturnsPurpose
harness@solverSolverHow the model is driven (single-turn, agentic, RAG…).
scorer@scorerScorerHow output is judged (match, LLM-judge, programmatic, human-stub).
dataset_loader—DatasetTurn a source (HF/S3/JSONL/DB) into a content-addressed snapshot.
tool@toolToolCapabilities an agentic harness can call.

Two properties make this safe and self-service:

  • Typed config with a published schema. Each plugin declares a Pydantic config model; its JSON Schema drives both RunSpec validation and the launch-wizard form — so a new plugin is immediately usable from the UI with no frontend work.
  • Versioned & reproducible. A plugin declares a semantic version (the label), while the actual executing code is pinned by the deployment's code_ref (git SHA) on the eval version (the truth). Reproducing a run means redeploying that code_ref.

v1 uses a shared in-process registry (entry-point discovery) with schemas derived live. A Postgres plugin catalog — which would let the control plane serve schemas without importing plugin code — is deferred until untrusted third-party plugins exist (it lands with multi-tenancy). It's purely additive: a table + a sync step.

Sandboxing — containing untrusted model code

Agentic evals execute untrusted, model-generated shell/code/file operations — the highest-stakes security surface in the system. The threat model is concrete: destructive/runaway actions (fork bombs, disk fill), network exfiltration or attacks on the engine's own services, attempts to reach cloud metadata (169.254.169.254) for node IAM credentials, sandbox escape, and adversarial-by-design evals that deliberately test dangerous capabilities.

The architectural lever In Inspect's model the agent loop runs in the worker; only tool/command execution runs in the sandbox. So the sandbox almost never needs to reach the model — which means most sandboxes can be fully air-gapped (zero egress), removing the single largest exfiltration vector for the majority of evals. This is the foundation of "air-gap by default."

Tiered isolation by eval risk

One size is wrong (microVMs for a calculator is wasteful; a shared container for a cyber eval is reckless). The harness declares its tier; the boundary criterion is sharp — not "how dangerous does it feel" but "is the model adversarially trying to escape?"

TierEval typeRuntime / boundaryNetwork
T1benign tools (search, calculator, RAG)hardened containerdeny-all + per-eval FQDN allowlist via a logged egress proxy
T2 (default)general agentic / code tasksgVisor — user-space kernel closes the kernel-exploit escape vectorair-gapped
T3cyber-offense, self-propagation, adversarialKata / microVM — a real per-pod VM; the boundary becomes the hypervisorfully air-gapped, dedicated nodes/account

gVisor (T2) reimplements the syscall surface in user space, which closes the kernel-CVE escape vector most container escapes rely on — plenty when the model just wants to solve the task. Kata (T3) gives each pod its own kernel, so you pay for VM isolation only when the eval rewards finding an exploit.

Baseline hardening (every tier)

  • Resource caps — CPU/memory/storage + a PID limit (kills fork bombs); storage limit kills disk-fill.
  • No credentials — no mounted secrets, zero-RBAC service account (automountServiceAccountToken: false), IMDS blocked so a sandbox can't lift node cloud credentials.
  • Network default-deny — a NetworkPolicy denies all ingress/egress; sandboxes cannot reach Postgres, the gateway, or each other. The rare legitimate need routes through a credential-less, logged egress proxy — a separate trust zone from the LiteLLM gateway (which holds provider keys), so sandboxed code can never spend the model budget or exfiltrate keys.
  • Pod security — non-root, read-only root filesystem, drop ALL capabilities, seccomp=RuntimeDefault, no host network/PID/IPC.
  • Node isolation — sandboxes on dedicated tainted node pools, away from control/ worker/gateway nodes, so an escape lands on a disposable node.
  • Guaranteed teardown — pods are single-use and TTL-bounded; a sweeper reaps any pod whose owning task's lease expired (labels carry run/sample id), so orphans can't accumulate.

The scale ceiling & its mitigation

Pod create/destroy throughput tops out at low-hundreds/s (K8s control-plane limits). v1 ships hardened per-sample pods — within budget while agentic is a minority of the aggregate — with cold-start hidden by pre-pulled images and expand-time pre-warm. The trigger-gated next step is a pooled microVM snapshot-restore service (T2): each sample runs in a fresh microVM restored from a golden snapshot in tens of ms, then discarded — fresh isolation and high churn, with no "prove the reset is airtight" burden because there's no reuse. (Detailed under Handling the load.)

Two distinct trust boundaries Don't conflate them: plugin code (harness/scorer/tool implementations) runs in the worker and is trusted via review; model-generated actions run in the sandbox and are untrusted, isolated by everything above. The sandbox protects against what the model does, not against a malicious plugin author.

Operations & observability

Two complementary surfaces, split by the question they answer — covered in the component reference; the operational rationale:

  • The Ops tab (/ops, eval_engine/ops.py) answers "is everything up right now?" Its portable backbone is a heartbeats table: the leader-elected orchestrator and every KEDA-churned worker upsert a liveness row each loop, so both become observable without coupling to the Kubernetes API — it works identically on GKE/EKS/AKS/local. It enriches with the in-cluster K8s API (pod phase, restarts, KEDA desired-vs-current) and one-click GCP Log Explorer deep links, and it degrades gracefully (an unreachable backend is a down card, never a 500). No log contents flow through the app — just a pre-filtered Log Explorer URL.
  • Grafana (/grafana) answers "how did metrics trend?" Five dashboards (Quality, Cost & Tokens, Fleet & Orchestration, Gateway, Infra) over three provisioned-as-code datasources: ClickHouse (eval quality, cost, latency), Postgres (live fleet/ ledger/budget state, orchestrator tick latency from the heartbeats), and Google Managed Prometheus (gateway QPS/latency/spend + pod CPU/mem/replicas). There's no Prometheus server to run — it reuses GMP, so the footprint is just a small Grafana pod.

A dedicated app /metrics exporter is deliberately deferred: the orchestration internals it would expose are already persisted in the heartbeats table (trended via Postgres), and the metrics that truly need counter/histogram semantics (gateway, infra) come from LiteLLM + GMP with no app code.

Training monitor — reuse as a feature (vNext)

eval_engine/training*.py · mock_trainer.py A vNext track that is the clearest demonstration of the platform's modularity. Training itself is an explicit non-goal, so the trainer is mocked; what's built is a continuous-eval / training-monitor layer that consumes a stream of checkpoints and drives the existing eval machinery against each one — then surfaces the per-checkpoint score trajectory with anomaly detection.

The reuse insight A checkpoint-eval is just a tagged Run. So the ephemeral ledger, KEDA workers, ClickHouse projection, retries, budget caps, transcripts, the Inspect viewer, and the Compare view all work unchanged. The net-new surface is thin: two entities, a few nullable columns, one poller/monitor loop, an anomaly module, and a UI tab — added without reshaping any hot path.

The monitor is one more leader-elected loop (the orchestrator pattern). Per tick:

  1. Discover — poll an object-storage prefix (the checkpoint.json manifest is the commit signal) and record new checkpoints. The watched prefix goes through the same fsspec wrapper, so it's gs://… in-cluster, a local dir in dev.
  2. Fan out — launch the eval suite as ordinary runs tagged with (training_run_id, checkpoint_id, step, sweep), with the checkpoint's opaque model_ref as the model (a mock resolver maps it to a real model — the rest of the engine never knows). Checkpoint-evals run in the interactive lane for timely feedback, with an eval-every + skip-stale backpressure valve.
  3. Reconcile — when a checkpoint's suite runs are terminal, roll their summaries into the per-(eval, step) score series with a Wilson CI, refit the expected curve, and run anomaly detection.
  4. Finalize — on the run going terminal, compute the best checkpoint per eval.

Anomaly detection & diagnosis

The hard part is telling a training fault apart from a model simply weak on a hard eval. The core metric is deviation from an expected trajectory (a saturating curve fit per eval), gated by the Wilson CI so sampling noise isn't flagged. Detectors yield regression / drift / plateau with a severity. The diagnosis then corroborates the eval score with orthogonal signals: a training-metric cross-check (loss vs. score quadrant), broad-vs-isolated collapse, canary evals (a trivial eval any functional model aces — its collapse is the decisive "model/serving broke" signal), error-rate vs. low-score, output-health (repetition/empty-output/refusal rate), and per-category regression. The result is a templated root-cause hypothesis with corroborating evidence — rendered as chart markers and a drill drawer.
