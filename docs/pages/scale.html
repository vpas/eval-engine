Where the numbers come from

~1,000 runs/day (~30k/month) sounds enormous, but it reflects a workload mix, not a huge sample count. A representative day: 

~300 full runs   × ~100k samples  = 30.0M
~700 subset runs × ~5k   samples  =  3.5M
                         per day  ≈ 33.5M sample-evals
                       per month  ≈  1.0B          → ~12B retained over 12 months
   sustained avg = 33.5M / 86,400s ≈ 385 samples/s   (bursty; higher at peak)

Many runs are small subsets for fast iteration, which is why the run count is high while the sample volume stays at ~1B/month. The two figures that genuinely force infrastructure survive this reconciliation intact: the ClickHouse sizing (~1B/mo, ~12B retained) and the claim QPS (~8/s at batch 50, low enough that a plain Postgres claim suffices).

The two forcing numbers Only (1) the 12B-row analytics store and (2) the global cross-worker rate limit demand heavyweight infrastructure (ClickHouse + Redis-coordinated LiteLLM). Everything else is sized to those two and kept minimal — that restraint is itself a scaling decision, because a simpler system has fewer ways to fall over.

Throughput — distribution & autoscaling

385 samples/s sustained (bursty above that) is not a single-box workload, so distribution is mandatory. The execution plane absorbs it by horizontal, stateless fan-out:

  • KEDA-autoscaled workers scale on count(queued) from zero up to a maxReplicas cap. Below the cap, worker count tracks queued work; at the cap, extra demand waits cheaply in the ledger rather than in over-provisioned pods. Workers run on a spot pool and scale to zero between runs.
  • No coordination overhead. Workers never talk to each other — the ledger claim is the only synchronization, so adding workers adds throughput linearly with no chatter.
  • Shard granularity. A worker claims a batch and runs it as one Inspect Task; the batch size defaults large for fast uniform QA and drops to 1 for high-variance agentic, matching the work to the harness.

Why a plain claim is enough

A common worry at fan-out scale is a thundering herd on the queue head. The arithmetic says it's a non-issue here: 

claim QPS = throughput / batch_size ≈ 385 / 50 ≈ 8 claims/s   (cluster-wide, at peak)

~8 claims/s — with typically <1 concurrent claim per run — is something a single Postgres laughs at, so the plain ordered FOR UPDATE SKIP LOCKED claim needs no hash-sharding. not_before already removes the poison-sample head-of-line problem. Hash-bucketing the claim is a deferred, purely additive optimization reserved for a different workload shape (batch≈1, sub-second samples, thousands of single-run claimers) — adding it later is a column + an index + a predicate, no migration.

Analytics — surviving 12B rows

The store is sized directly to the forcing number. The design choices that make 12B rows tractable:

PressureHow it's absorbed
~1B inserts/month, burstyAsync-insert with server-side batching → one part per shard, no write-amplification under many concurrent workers.
12B rows to scan/sliceColumnar storage + LowCardinality dimensions + an ORDER BY keyed on the actual filter columns (eval, model, run).
12-month retentionMonthly partitions aligned to the TTL → expiry is a partition drop, not a delete.
Exact headline metricsComputed once at finalize with FINAL over the deduped run partition (~100k rows) — cheap, never a full-table merge.
Live progress on ~50 runsRead without FINAL, throttled to ~once/minute, on the full sort-key prefix so it hits a tight index range, not a billion-row scan.

The control plane never grows with this: the ledger is ephemeral, so Postgres only ever holds the in-flight slice (tens of runs × up to 100k tasks), pruned on finalize. The 12B rows live exclusively in ClickHouse.

The global rate limit

The second forcing requirement. With a mix of API providers (hard quota) and self-hosted vLLM (finite capacity), the cap on calls-in-flight must be global across all workers and gateway replicas — a per-pod limit would let N replicas collectively blow a provider quota. The solution:

  • All traffic through LiteLLM (≥2 replicas), with per-model rpm/ tpm caps enforced pre-call against Redis-shared counters (usage-based-routing-v2). The cap is a counter under a hashed key that every replica reads — so it protects provider quota cluster-wide.
  • Fail-fast, retry at the worker. num_retries: 0 means an over-cap call gets an immediate 429, which the worker's retry-with-backoff handles — pushing the wait into the ledger (cheap) rather than holding a gateway connection.
  • Load-tested. Filling a bucket on one gateway replica caused a different replica to return 429 for the same model, proving the cap is shared via Redis, not per-replica. (Fully synchronized bursts can briefly overshoot via a read-then-increment race, then converge — acceptable for quota protection.)

Admission keeps small runs fast under load

At peak (~50 concurrent runs) the scaling risk shifts from throughput to latency fairness: a quick iteration run mustn't starve behind big batch runs. The two-lane admission + per-run max_inflight cap solve exactly that with constants — a big run can't consume the whole cluster, so any newly-admitted run always makes progress, and a reserved interactive slice guarantees quick runs get slots now. No per-tick allocator is built, because at this scale (mostly one team) there is almost no weighted team contention to arbitrate.

The one acknowledged ceiling — agentic churn

The honest scaling limit is agentic sandboxing. Pod create/destroy throughput (not boot latency) tops out at low-hundreds/s due to Kubernetes control-plane limits (scheduler/kubelet/IPAM/gVisor-boot). v1 ships per-sample pods, which is within budget while agentic is a minority of the 385/s aggregate — the common early case. Cold-start is hidden by pre-pulled images and expand-time pre-warm.

Gated on a measured trigger When agentic volume approaches the per-sample-pod ceiling, the mitigation is a pooled microVM snapshot-restore sandbox service that keeps the kube-scheduler out of the per-sample path — a trigger-gated future build, not a v1 cost. Warm pools of pre-booted pods were considered and dropped: they hide cold-start latency but don't move the create/destroy throughput ceiling. This is the system's top-tier scaling risk and is explicitly gated on a churn spike.

Designed headroom vs. deferred work

Several scaling levers are intentionally not built yet, each because the current load doesn't require it and each additive when it does — so they're triggers, not gaps:

LeverRe-introduce when…
Weighted fair-share schedulermultiple teams with different weights measurably starve each other under shared capacity.
Direct (gateway-bypass) vLLM pathin-cluster inference carries load and the gateway proxy is the measured bottleneck (thousands of calls/s).
Pooled microVM sandboxagentic create/destroy throughput exceeds the per-sample-pod ceiling.
Hash-bucketed claimthe batch≈1 / sub-second / thousands-of-claimers regime appears.

The net: the system is built to the load it actually has, with a documented, additive path to the next order of magnitude on each axis — and no speculative complexity on the critical path before the workload proves the need.
