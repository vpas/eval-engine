How it works

Execution & orchestration

This is the custom IP — the part most likely to harbor correctness bugs, so it is the part specified most carefully. Three goals drive every mechanism below: (1) no completed sample is ever lost, (2) no sample's effects are double-counted (at-least-once execution → effectively-once results), and (3) every state is crash-recoverable and idempotent on re-entry.

The design stance The Postgres ledger is the single source of truth for execution state. No critical coordination lives in worker memory. Any component can die at any time; recovery is always "re-derive from the ledger." That is the entire reason for choosing a ledger over an in-memory controller — so the system leans on it fully.

A run, end to end

  1. A user defines an eval + picks a model and config → POST /runs (authenticated via OIDC). The API validates the RunSpec's plugins against the registry.
  2. The API launches: it loads the dataset, classifies the run into a lane, creates the runs row (queued), and expands the dataset slice into sample_tasks ledger rows. It returns 202 immediately.
  3. The orchestrator admits the run (queued → running) under the two-lane policy.
  4. Workers atomically claim a shard, run it as one Inspect Task (model calls via the gateway, then scorers), and commit each result.
  5. Per sample: transcript → object store; result inserted to ClickHouse with a durable ack; then the ledger row flips done. Transient failures retry with backoff; permanent ones are recorded.
  6. When the ledger is fully terminal, the orchestrator finalizes: aggregate metrics into the run, archive failures, prune the ledger.
  7. Analyze via the dashboard's ClickHouse-backed views + the Inspect viewer. Reproduce by cloning the RunSpec.

Every transition is a single guarded SQL UPDATE and idempotent on re-entry. Expansion is INSERT … ON CONFLICT DO NOTHING; the running → finalizing condition is a pure query (safe to re-evaluate); finalize steps all recompute or no-op on a second pass. So a crash in any state is recovered by simply re-running the tick.

Claim, lease & retry

Workers do not talk to each other. The ledger claim (FOR UPDATE SKIP LOCKED) is the only scheduler. Three mechanisms keep at-least-once execution safe and progress-making:

MechanismWhat it doesWhy it's safe
Lease A claim sets lease_expires_at = now() + 10min. A long agentic/SWE batch renews it from a background heartbeat thread. If a worker dies, renewal stops, the lease lapses, and the claim query reclaims the running row. No lost work.
Retry with backoff A transient sample error re-queues with exponential not_before backoff up to MAX_ATTEMPTS (default 3), then goes terminal failed. not_before gates re-claim, so a poison sample backs off instead of head-of-line blocking the queue. A merely low score is not a failure.
Per-run cap The claim is bounded by headroom = max_inflight − live_running. A big run can't eat the cluster; workers flow to runs with headroom. The fairness primitive.

Errors are taxonomized: RetryableError (429, timeout, transient tool/network) retries; FatalError (malformed sample) and the terminal BudgetExceeded do not. Because all result writes are keyed by (run_id, sample_id) and dedup in ClickHouse, a wrongful reclaim (e.g. a missed heartbeat) is wasted compute, never corruption.

The commit protocol — ack-before-flip

This is the heart of "no completed sample is ever lost." ClickHouse is bad at many tiny inserts and we need exactly-once analytics despite at-least-once execution. The result path solves both. Per shard, the commit is an ordered, ack-gated, idempotent write where the ledger flip is the single commit point: 

1.  write each transcript → object store      (idempotent, deterministic key)
2.  async-insert the shard's results → ClickHouse with wait_for_async_insert=1
        └─ BLOCK until ClickHouse durably acks the rows (in a part, not just buffered)
3.  ONLY THEN flip the ledger rows  status = 'done'  (+ loaded)
The invariant status = 'done' ⟹ the result is durable in ClickHouse. A crash before the flip leaves the row running → the lease expires → the shard re-executes → the transcript re-writes to the same key and the ClickHouse re-insert collapses via ReplacingMergeTree((run_id, sample_id)). Atomicity becomes ordering + idempotency (write the data durably, then commit the pointer), not a distributed transaction. wait_for_async_insert=1 still server-batches across workers, so batching is preserved.

The implementation is runner.commit_batch: it inserts the clean results, then flips each ledger row, then marks loaded — reading the attempt count before the flip so the ClickHouse row carries the correct ReplacingMergeTree version.

Exactly-once analytics

At-least-once execution (lease reclaim, retries) means a sample can be computed more than once. Two things make the results effectively-once:

  • ReplacingMergeTree keyed on the sample. A re-execution writes the same key with a higher attempt (the engine version); the newer result wins and a duplicate re-insert collapses on merge / FINAL.
  • Headline metrics computed once at finalize. The run summary is computed over the deduped partition with FINAL — not by an insert-time materialized view, which would fire per insert block and never see the later collapse, double-counting a re-loaded batch. In-progress numbers come from the gateway (cost) + ledger counts (progress), which can't double-count.

Live metrics

Rather than incrementing a hot done_samples counter on every sample (100k contended writes/run), the orchestrator derives the rollup each tick and writes it once to the runs row: progress from ledger status counts, cost from the committed ledger rows, and a live accuracy. Clients read live and final numbers from one authoritative place (the runs.status distinguishes them). A subtlety: the live ClickHouse score read uses the full (eval_id, target_id, run_id) sort-key prefix — filtering on run_id alone (the 3rd key column) can't use the index and would scan the whole month's partition.

Budget enforcement

A run can carry a budget_usd cap. Defense in depth, two layers:

  • Soft stop (orchestrator). Each tick it reads committed cost; once it reaches the cap it converts still-queued tasks to a distinct terminal status budget_skipped (error type budget_exceeded). Workers also enforce this to stop claiming early.
  • Why a distinct class. budget_skipped is not failed — so it neither inflates the failure count (which would trip spurious fail-fast) nor burns retries. In-flight samples finish naturally; the run finalizes with status budget_exceeded.

The canonical form (a per-call gateway reject tagged by run_id) enforces the same semantics at the gateway; the control-side sweep is the v1 implementation.

Cancellation

Default = graceful drain. On cancel, the run flips to cancelled (a guarded atomic update that can't race the orchestrator into a double-finalize), queued tasks are marked terminal, and a worker's already-claimed batch finishes and commits harmlessly against soon-pruned rows. The committed counts are snapshotted and the ledger pruned — the run settles like any other terminal run. Partial results stay queryable. Cancelling from queued/expanding is immediate.

Finalization & pruning

  1. Barrier. All tasks terminal. Because of ack-before-flip, done already implies durable in ClickHouse — there is no separate "loaded" wait.
  2. Aggregate. Compute pass_rate, mean score, CI, tokens from ClickHouse (FINAL, full sort-key prefix) + cost from the gateway tally → write onto the run.
  3. Archive & prune. Copy failed task rows to a durable failed_task_archive (for post-hoc debugging), then DELETE FROM sample_tasks WHERE run_id=$1. Keeps Postgres tiny while preserving the only per-task history anyone wants later.

Every sub-step is idempotent, so a crash mid-finalize just re-runs the no-ops.

Admission & scheduling

At ~1,000 runs/day with mostly one team, there is little weighted team contention to arbitrate — so v1 does not build a fair-share allocator. The real risk is head-of-line latency: a quick 50-sample iteration run stuck behind big full-dataset runs. The fix is constants + an admission comparator, no per-tick allocator:

  • Global cap on concurrently-running runs (default 50) — blast radius + shared provider quota.
  • Two lanes. A run is classified interactive (a limit, or ≤200 samples) or batch at launch; an explicit lane overrides. Interactive uses a small per-run max_inflight (5 — many iterators progress); batch uses a larger one (50).
  • Reserved, borrowable interactive slice (default 12 ≈ 25%). Batch can borrow it only when there is no interactive demand, and yields by attrition when an interactive run arrives — never mid-run preemption.

The whole policy lives at the admission boundary; the per-run max_inflight is then enforced for free inside the claim's LIMIT. KEDA scales workers on count(queued) with a maxReplicas cap so worker count never outruns what the serving tier can feed.
