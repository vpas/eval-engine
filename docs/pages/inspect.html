Foundations

Integration with Inspect AI

Building an eval execution kernel — dataset → solver → scorer, with tool use, sandboxing, model-graded scoring, and transcript logging — is a large, solved problem. Eval Engine adopts Inspect AI directly as that kernel and spends its effort on the differentiated platform around it: distributed orchestration, the ClickHouse analytics projection, and the dashboard. We call this stance Inspect-native.

What "Inspect-native" means

It is a stronger claim than "we use Inspect." There is no wrapper layer re-abstracting Inspect's types:

  • Harnesses are Inspect Solvers.
  • Scorers are Inspect Scorers.
  • Workers call inspect_ai.eval(...) directly.
  • The Inspect .eval log is our source-of-truth artifact in object storage.

Inspect's Dataset → Solver → Scorer abstractions match the domain model 1:1, which is the whole reason the composability guarantee (any model × harness × dataset × scorer) is cheap to uphold. We accept the coupling deliberately and would only extract an interface if a genuinely non-Inspect backend were ever needed.

The consistency rule Being Inspect-native does not make Inspect's log format the analytics store. Every completed sample is flattened (ETL'd) into ClickHouse for querying. The .eval log is the immutable artifact; ClickHouse holds the queryable projection. That projection is indexing, not an abstraction layer — so it stays consistent with the Inspect-native stance.

The plugin layer wraps Inspect's registry, thinly

eval_engine/plugins.py · builtins.py The platform adds a thin, typed, discoverable layer around Inspect's own registration — it wraps registration + config + metadata, not the Inspect types. A harness/scorer is a factory keyed by (kind, name, version) that returns an Inspect object, plus a Pydantic config model whose JSON Schema drives RunSpec validation and the launch-wizard form. 

@harness("agentic", "1.0.0", AgenticConfig, description="Tool-using agent loop, K8s-sandboxed.")
def agentic(cfg) -> tuple[Solver, SandboxEnvironmentSpec]:
    return basic_agent(tools=[...], max_attempts=cfg.max_steps), sandbox_spec

@scorer("llm_judge", "1.0.0", JudgeConfig, primary_metric="score")
def llm_judge(cfg) -> Scorer:
    return model_graded_qa(model=cfg.judge_model, template=cfg.rubric)

The built-in catalog already spans the major eval shapes:

Harnesses: single_turn multiple_choice agentic code_generation swe_bench

Scorers: includes match choice llm_judge math numeric_answer code_exec ifeval swe_bench

A RunSpec references plugins by {type, version, config}; the control plane validates them against the registry at launch, and the worker resolves them at execution time into the Inspect Solver/Scorer objects. Multiple scorers compose as an Inspect scorer list. See Extensibility for the full plugin contract.

Where the kernel plugs in — the worker call

eval_engine/runner.py A worker that has claimed a shard builds one Inspect Task and runs it. This is the exact seam between the platform and the kernel: 

sub      = MemoryDataset([samples_by_id[i] for i in claimed_ids])
solver, sandbox = plugins.build("harness", spec.harness)     # → an Inspect Solver (+ sandbox spec)
scorers  = [plugins.build("scorer", s) for s in spec.scorers] # → Inspect Scorers
task     = Task(dataset=sub, solver=solver, scorer=scorers, sandbox=sandbox)

inspect_log = inspect_ai.eval(
    task, model=model, log_dir="gs://…/eval-logs",   # the .eval artifact
    epochs=epochs, time_limit=SAMPLE_TIME_LIMIT,      # sampling + hung-call cap
    temperature=…, seed=…, timeout=MODEL_TIMEOUT,     # GenerateConfig
    fail_on_error=False)[0]                           # one bad sample doesn't sink the shard

Three integration details worth calling out:

  • Models route through the gateway. Inspect's provider-agnostic model layer is pointed at LiteLLM (OPENAI_BASE_URL=http://litellm:4000/v1), so all the platform's rate-limiting and cost accounting apply to every Inspect model call with no kernel change.
  • Epochs for statistical comparability. Inspect's epochs repeats each sample N times and reduces to one per-sample score — the basis for the Wilson confidence interval the dashboard shows. Outputs are comparable, not bitwise (hosted models are non-deterministic even at temperature=0).
  • Per-sample errors are first-class. The platform reads Inspect's per-sample .error (a model/tool/sandbox exception, distinct from a low score) and routes it into retry-with-backoff; fail_on_error=False keeps the rest of the batch moving.

Sandboxing via Inspect's K8s provider

Agentic harnesses return a sandbox spec alongside the solver; Inspect's Kubernetes sandbox provider provisions an ephemeral pod per sample and runs tool/command execution inside it. The platform hardens those pods (gVisor, air-gap, resource caps) and guarantees teardown with a sweeper. Crucially, the agent loop runs in the worker and only tool execution is in the sandbox — an Inspect architectural fact that lets most sandboxes be fully air-gapped. Inspect's default Docker sandbox was rejected on Kubernetes (it needs Docker-in-Docker or a host socket — privileged anti-patterns); the K8s provider avoids that. See the sandbox tiers.

The embedded viewer & the ETL projection

Two outputs flow from each Inspect eval:

  • The .eval log → object storage, served by the embedded Inspect viewer for rich per-sample traces (the dashboard deep-links to the exact sample).
  • A flattened row → ClickHouse, extracted from the Inspect log: scores, the primary score/pass, token usage, the provider's resolved model + system fingerprint, and the transcript URI. This is the ETL projection that keeps analytics fast and insulated from the log format.

The coupling, and how it's managed

The Inspect-native bet is an accepted risk: the platform is genuinely coupled to Inspect's types and log format. Two things keep that safe. First, the ClickHouse projection insulates analytics — queries never touch the .eval format, so an Inspect change can't ripple into the dashboard's analytics. Second, the coupling buys so much (the entire kernel) that re-implementing it would be the larger risk. Inspect is actively developed by the UK AISI and trending toward a de-facto standard, which is why adopting it directly — rather than hedging behind an abstraction with no second implementation to justify it — is the deliberate choice.
