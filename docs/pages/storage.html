How it works

Storage choices, justified

Four storage tiers, each chosen for one job and defensible against the load envelope. The guiding split: hot coordination in Postgres, cold analytics in ClickHouse, immutable artifacts in object storage, soft shared counters in Redis. Putting any one job in the wrong tier is what breaks at scale — this page explains why each lives where it does.

TierHoldsWhy this engine
Postgres run metadata, the ephemeral task ledger, registry, audit, heartbeats, leader lock Transactional row-locking (FOR UPDATE SKIP LOCKED) + SQL aggregates over live state.
ClickHouse the ~12B-row per-sample results projection Columnar OLAP built for billions of rows + fast slicing; deduping merge engine.
Object store .eval logs, transcripts (zstd), dataset snapshots Cheap, durable, infinitely scalable blob storage; tiering for the dominant cost.
Redis global rate-limit counters, per-run stop-flags Fast shared, atomic counters across gateway replicas; state is soft/rebuildable.

Postgres — the coordinator

Why Postgres for the ledger

The task ledger needs three things a plain message queue can't give: atomic claim with no double-dispatch, lease-based crash reclaim, and the ability to answer SQL-shaped questions about live state (counts by status, per-lane running counts, budget burn, fairness). Postgres' FOR UPDATE SKIP LOCKED is exactly an atomic work-claim primitive, and the rest is just SQL over the same rows. The ledger is our domain model that happens to use a standard claim pattern — not a generic queue we're reinventing.

Rejected: Temporal / SQS A workflow engine is the wrong shape — our work is a single-step fan-out (claim → run one sample → record), not a multi-step workflow, so we'd use almost none of it. Worse, its own persistence becomes the same ~1B/month write problem we already solve, and it can't answer the SQL questions the control plane asks. pgmq/procrastinate remain a drop-in escape hatch if the hand-rolled lease ever proves bug-prone.

Why the ledger is ephemeral and skinny

Two deliberate constraints keep Postgres tiny and fast despite 12B lifetime samples:

  • Ephemeral. sample_tasks holds only in-flight runs; on finalize, failures are archived and the rest pruned. Lifetime history lives in ClickHouse + object storage, so Postgres never grows a 12B-row table.
  • Skinny. The ledger carries only coordination (status/lease/attempts/error). Results go straight to ClickHouse — they never widen the ledger row.
Reversed: widened rows + a ResultLoader An earlier design wrote fat result payloads into the ledger row and had a separate loader copy them to ClickHouse. Co-locating tiny hot coordination updates with fat append-mostly columns on one high-churn table caused dead-tuple / autovacuum bloat at 1B/month. The skinny ledger + direct async-insert deleted both the bloat and a whole component.

Managed Neon

In this deployment Postgres is managed Neon serverless (external, free tier) — zero always-on DB cost, its own storage durability and failover. The app connects through Neon's pooled (PgBouncer) endpoint via a bounded psycopg_pool; the leader lock uses a session-mode endpoint (a transaction pooler would defeat the advisory lock — see Resilience). The portability contract is vanilla Postgres only — no Aurora-only features — so CloudNativePG or any managed Postgres is a drop-in.

ClickHouse — the 12B-row analytics store

Why ClickHouse

This is one of the two numbers that force real infrastructure. At ~1B new rows/month and ~12B retained, the analytics store must do wide columnar scans, group-bys, and percentile work over billions of rows — and TTL-drop a year-old month cheaply. That is ClickHouse's home turf and squarely outside Postgres' or DuckDB's comfort zone.

  • Columnar + LowCardinality on provider/model/harness/category shrinks 12B rows and makes model-comparison scans fast.
  • Monthly partitions aligned to the 12-month TTL turn retention into a cheap partition drop, not a row-by-row delete.
  • A deduping merge engine (ReplacingMergeTree) is what makes exactly-once analytics fall out of at-least-once execution (see Execution).
DuckDB stays dev-only DuckDB is great for local-dev and one-off spikes, but 12B rows is well past its comfort zone as a shared, concurrently-written warehouse. It remains the local stand-in, not the production store.

The table

CREATE TABLE sample_results (
  run_id, sample_id, eval_id, eval_version,
  provider LowCardinality, model_id LowCardinality, harness_type LowCardinality,
  group_key LowCardinality,                 -- category / slicing dimension
  passed UInt8, primary_score Float64, scores String,   -- all scorer outputs as JSON
  tokens_in, tokens_out, cost_usd, latency_ms, attempt,
  error_type LowCardinality, transcript_uri, review_status, finished_at DateTime )
ENGINE = ReplacingMergeTree(attempt)          -- newest re-execution wins; dup re-insert collapses
PARTITION BY toYYYYMM(finished_at)
ORDER BY (eval_id, model_id, run_id, sample_id)
TTL finished_at + INTERVAL 12 MONTH

The ORDER BY front-loads the columns most queries filter on (which eval, which model), so it doubles as both the access-pattern key and the dedup key. The passed/ primary_score columns are hoisted out for the fast common path while the full scores map keeps the table flexible across arbitrary scorers with no per-eval schema change.

Reversed: insert-time aggregating MV An insert-time AggregatingMergeTree materialized view for per-run pass-rate/cost was rejected: it fires per insert block and never sees the base table's later ReplacingMergeTree collapse, so a re-loaded batch double-counts the headline numbers. Computing once at finalize over the deduped partition is exactly-once by construction.

Why workers insert directly

Workers async-insert straight to ClickHouse (async_insert=1, wait_for_async_insert=1) — the server batches concurrent small inserts into one part (no write-amplification under load) while still blocking until durable, which is what lets the ack-before-flip commit hold its invariant. No separate loader exists; ClickHouse's own server-side buffering is the batching layer.

Object storage — immutable artifacts

Why object storage

The bulky, write-once artifacts — Inspect .eval logs, per-sample transcripts, and dataset snapshots — belong in cheap, durable, effectively-infinite blob storage, not a database. The .eval log is the source-of-truth artifact; ClickHouse is just the index over it.

Transcript storage is the dominant cost — so it's managed

  • zstd compression on every transcript (.json.zst).
  • Sample-by-default retention — keep all failures (what you debug) plus a deterministic fraction of passes (stable in/out by a hash of the sample id), with a per-eval opt-in to keep everything. The ClickHouse projection stays full-fidelity regardless.
  • Storage-class tiering — a lifecycle policy cools objects to NEARLINE at 30 days, COLDLINE at 90.
Why sample, not keep-all The asymmetry is the point: keep-all's sunk storage cost is not reversible downward, while sampling is reversible upward — you can always decide to keep more later. So the cheaper default is also the safer one.

Portable by interface (fsspec)

All object-store access goes through one storage.py fsspec wrapper where the URI scheme selects the driver — gcsfs for gs://, s3fs for s3://, a local path in dev. No native cloud SDK appears in app code, so AWS S3, GCS, or self-hosted MinIO are all swappable with zero code change. Credentials come from the environment (workload identity / the node service account).

Datasets are content-addressed

Registering a dataset hashes its bytes and writes an immutable snapshot keyed by that hash; the content_hash + snapshot_uri are pinned on the dataset version. A RunSpec pins the version → the hash → the exact bytes, giving true input reproducibility (and free dedup: identical content → identical hash). LakeFS/DVC/HF-revisions were considered and not adopted as the system-of-record — content-addressed snapshots are the simplest thing that gives real reproducibility with no extra stateful service; LakeFS can slot under the same pointer later if branching is ever needed.

Redis — soft shared state

Redis holds exactly the state that must be shared, atomic, and fast across gateway replicas but is soft and rebuildable: the global per-model rate-limit counters and the per-run stop-flags. It is the substrate that makes the cross-worker rate limit — the second forcing requirement — possible: a read-modify-write counter under a hashed key, shared by all LiteLLM replicas.

Because the state is soft, a Sentinel failover losing a sliver of a rate-limit window is acceptable — which is why a 3-pod + Sentinel cluster is enough and no durable store is warranted here. Putting rate-limit counters in Postgres would add contention to the coordinator for data that doesn't need durability; putting them in worker memory would defeat the "global, cross-worker" requirement entirely.

One-line rationale per tier

Postgres

Needs transactional claims + SQL over live state. Ephemeral + skinny so it never grows huge.

ClickHouse

Needs billion-row columnar scans + cheap TTL drops + dedup-on-merge. Forced by the 12B-row figure.

Object store

Needs cheap, durable, write-once blobs at any scale. Tiered + sampled because transcripts dominate cost.

Redis

Needs fast atomic counters shared across replicas; state is soft, so HA-by-Sentinel suffices.
