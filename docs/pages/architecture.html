Architecture

Architecture & components

Eval Engine is two cooperating planes that meet only at Postgres. This page walks every component from the diagram on the overview — its job, the code that implements it, and how it is deployed.

One image, many roles The whole backend ships as one container image (deploy/Dockerfile); the role is chosen by the launch command — uvicorn eval_engine.api:app (API), python -m eval_engine.orchestrator, python -m eval_engine.worker, or the training monitor. Shared types and storage code, no per-service duplication.

The two planes

PlaneComponentsCardinalityOwns
Control Dashboard, FastAPI, Orchestrator, Inspect viewer, Postgres API: N replicas · Orchestrator: 1 active (leader-elected) Humans & durable state: accept launches, expose status/results, admit + finalize runs.
Execution Workers, sandbox pods, LiteLLM gateway, Redis Workers: 0…N (KEDA) · Gateway: ≥2 Compute: claim a shard, run the Inspect Task, call models, commit results.

Because the planes share nothing but the Postgres ledger, they scale independently: the API can be redeployed without touching in-flight work, and workers can scale to zero between runs while the control plane stays up.

Access edge — ingress, TLS, OIDC

deploy/k8s/61,62 There is exactly one public entrypoint. An nginx Ingress terminates TLS (a Let's Encrypt certificate auto-issued by cert-manager) on a stable nip.io host derived from a reserved external IP. All traffic is routed to oauth2-proxy, which authenticates against Google OIDC before proxying to anything behind it — so both the dashboard and the raw API are gated by the same login.

  • oauth2-proxy injects the authenticated user's email as a header; the API reads it (X-Forwarded-Email, falling back to X-Auth-Request-Email) as created_by on every run and as the audit-log actor.
  • The reserved IP keeps the host — and therefore the registered OAuth redirect URI — stable across cluster rebuilds, so a migration never re-touches OAuth.
  • Grafana sits behind the same gate at /grafana; the Inspect viewer at /inspect/.

Dashboard (Next.js)

frontend/ A Next.js App-Router app in a dark "lab instrument" theme. It is a pure client of the control API (it proxies /api/* → the FastAPI service) and renders:

  • Runs list / detail — live status pills, accuracy bars with confidence intervals, per-category breakdown, the full reproducible RunSpec, and a per-sample table that drills into transcripts.
  • Launch drawer — builds a RunSpec from the live /catalog of registered harnesses/scorers; toggles between an ad-hoc launch and launching from a registered eval.
  • Compare — diff two runs (also reused to diff two training checkpoints).
  • Operations tab and Training tab (see Observability and Training monitor).
  • Embedded Inspect viewer link for rich per-sample traces.

Control-plane API (FastAPI)

eval_engine/api.py The stateless HTTP control plane. In the cluster it is launch-only: POST /runs validates the RunSpec's plugins, creates the run, and expands the ledger — then returns 202 immediately. The orchestrator and workers do the actual execution. (A EVAL_ENGINE_API_INLINE_EXEC=1 toggle runs the whole pipeline inline for local dev.)

Reproducibility is built in: re-run clones a stored RunSpec into a new run with identical pinned inputs, and registered entities are immutable versions (re-register to mint a new version — no PUT/DELETE), matching the content-addressed stance of the data model.

Orchestrator

eval_engine/orchestrator.py A single leader-elected singleton running one "derive state each tick" loop (default every 2s). It runs ≥2 replicas for a warm standby; only the leader ticks, holding a Postgres session-scoped advisory lock. Each tick:

  1. Admit (_admit) — two-lane admission moves queued runs to running under a global cap with a reserved interactive slice (details).
  2. Reconcile — for each running run, publish a live rollup (done/failed/accuracy/ cost) onto the runs row, and enforce its budget cap.
  3. Finalize — a run whose ledger is fully terminal gets a safety-sweep load, then aggregate → archive failures → prune the ledger → mark completed (or budget_exceeded). The gate keys on the run's authoritative total so a still-expanding run is never finalized early.
  4. Housekeeping — heartbeat, prune old heartbeats, and (throttled) reap orphaned sandbox pods.
It governs efficiency, not safety The orchestrator's death just lets live state go stale for a few seconds until the standby takes over — the durable ledger is untouched, and in-flight workers keep going without it. See leader election.

Inspect log viewer

eval_engine/view_main.py · deploy/k8s/85 The official Inspect viewer, embedded behind the OIDC ingress at /inspect/, serving the .eval logs that workers write to gs://…/eval-logs. Rather than rebuild a transcript UI, the platform embeds Inspect's own. The patched entrypoint injects a FileMappingPolicy so the viewer only ever sends relative log basenames — the fix for a subtle bug where oauth2-proxy's path-normalization collapsed gs:// double-slashes and 404'd every read. The dashboard deep-links from a sample straight to its exact trace.

Training monitor (vNext)

eval_engine/training.py · mock_trainer.py A separate leader-elected loop (same pattern as the orchestrator) that watches an external — and, in v1, mocked — trainer's checkpoint stream and continuously evaluates each checkpoint. Training itself is an explicit non-goal; this layer only consumes checkpoints. Its key insight: a checkpoint-eval is just a tagged Run, so the ledger, workers, ClickHouse projection, retries, budgets, transcripts, and the Compare view are all reused unchanged. Per tick it discovers new checkpoints from an object-storage prefix, fans out the eval suite as ordinary runs, reconciles their scores into a per-step trajectory, and runs anomaly detection that distinguishes a training fault from a model simply weak on a hard eval. Covered in depth on the Extensibility page.

Postgres — metadata + the ephemeral ledger

eval_engine/control.py · managed Neon Postgres is the coordinator of the whole system. It holds run metadata, the entity registry, the audit log, heartbeats, the leader-election lock, and the ephemeral sample-task ledger — the table that is the sole scheduler.

The ephemeral ledger

sample_tasks holds only in-flight runs. When a run finishes it is archived (failures only) and pruned — so Postgres stays tiny despite ~12B lifetime samples. The ledger is deliberately skinny: it carries coordination state (status, attempts, claimed_by, lease_expires_at, not_before) — results never widen it; they go straight to ClickHouse.

The core primitive is an atomic claim — FOR UPDATE SKIP LOCKED over row locks:

UPDATE sample_tasks t SET status='running', attempts=attempts+1, claimed_by=$worker,
       lease_expires_at = now() + lease
FROM ( SELECT run_id, sample_id FROM sample_tasks
       WHERE run_id=$run
         AND ( (status='queued' AND (not_before IS NULL OR not_before <= now()))
            OR (status='running' AND lease_expires_at < now()) )   -- reclaim dead leases
       ORDER BY sample_id
       LIMIT LEAST($batch, max_inflight − live_running)             -- per-run concurrency cap
       FOR UPDATE SKIP LOCKED ) c
WHERE t.run_id=c.run_id AND t.sample_id=c.sample_id RETURNING t.sample_id;

FOR UPDATE SKIP LOCKED gives at-least-once execution with no double-claim; the lease reclaims a dead worker's tasks; not_before backs off poison samples; and the max_inflight headroom is the load-bearing fairness primitive. See Execution for the full lifecycle and Storage for why Postgres is the right home for this.

Connection handling

The whole process shares one bounded psycopg_pool.ConnectionPool (autocommit, default max 10) that liveness-checks a connection on checkout; a _run() wrapper retries dropped backends with bounded backoff. This turns a Neon failover/cold-start from a crash-loop into a silent recovery. The one exception is the leader lock's dedicated session-mode connection (a transaction pooler would defeat the advisory lock — see Resilience).

Workers (KEDA-scaled)

eval_engine/worker.py · runner.py · deploy/k8s/50,70 A stateless Kubernetes Deployment, autoscaled by KEDA on ledger queue depth (scale to 0 when idle, up to a cap). Workers run on a spot node pool — eviction is a non-event because the lease reclaims their tasks. There is no inter-worker coordination; each worker is just a copy of the loop: 

claim a batch  →  run it as ONE Inspect Task  →  commit (ack-before-flip)  →  load
  • Shard = one Inspect Task. A worker claims a batch of sample-tasks and runs them as a single inspect_ai.eval call (model calls via the gateway, scoring inline).
  • Lease heartbeat. A background daemon renews the lease while a long batch (agentic / SWE-bench) executes, so it isn't wrongly reclaimed mid-flight; if the worker dies, renewal stops and the lease lapses → reclaim.
  • Graceful drain. On SIGTERM (rollout/scale-down) the worker stops claiming new batches, finishes the in-flight one, and exits — so a rolling update never strands tasks. terminationGracePeriodSeconds is set above the per-sample timeout.
  • Hung-call protection. A per-request model timeout and a per-sample wall-clock limit ensure one stuck call can't wedge the worker; a breach surfaces as a retryable error.

Agentic sandbox pods

deploy/sandbox/ · deploy/k8s/90 · docs SANDBOXING Agentic evals execute untrusted, model-generated code — the highest-stakes security surface. The platform uses Inspect's Kubernetes sandbox provider: each agentic sample gets a fresh, hardened, ephemeral pod that is torn down on exit. A crucial property keeps this safe and cheap: the sandbox never calls the model — the agent loop runs in the worker, only tool/command execution happens in the pod — so most sandboxes can be fully air-gapped (zero egress).

Isolation is tiered by eval risk (the harness declares its tier):

TierEval typeRuntimeNetwork
T1benign tools (search, calculator, RAG)hardened containerdeny-all + allowlist via egress proxy
T2 (default)general code executiongVisor (user-space kernel)air-gapped
T3dangerous capability (cyber, self-propagation)Kata / microVMfully air-gapped, dedicated nodes

Every tier gets baseline hardening (resource + PID caps, no credentials, IMDS blocked, default-deny NetworkPolicy, non-root read-only rootfs, dropped capabilities, dedicated tainted node pool). An orchestrator sweeper reaps any pod whose owning task's lease expired, so orphans can't accumulate. v1 ships per-sample pods with gVisor (T2) as default; a pooled microVM snapshot-restore service is the trigger-gated next step if agentic churn ever approaches the pod-create throughput ceiling. Full threat model on the Extensibility page.

LiteLLM gateway

deploy/k8s/30-litellm.yaml All model traffic — external API providers and self-hosted vLLM alike — goes through LiteLLM (≥2 replicas). Workers call it OpenAI-compatibly (OPENAI_BASE_URL=http://litellm:4000/v1). One path means one rate limiter, one cost tally, one place for fallback. It provides:

  • Global rate limiting — per-model rpm/tpm caps shared across replicas via Redis (usage-based-routing-v2 + enable_pre_call_checks), so the cap protects provider quota cluster-wide, not per-pod. num_retries: 0 → fail-fast 429 (the worker's retry-with-backoff handles it). This is one of the two load-forcing requirements.
  • Cost accounting — the gateway's per-run_id spend is the canonical cost source by design. (Today the platform prices from the OpenRouter catalog the gateway fronts, which equals the gateway figure in dollars; querying the gateway's own tally is a deferred refinement.)
  • Resilience tuning — allowed_fails: 3 + a short cooldown so one bad upstream doesn't cascade the whole deployment down.

Redis (HA)

deploy/k8s/11-redis-ha.yaml A 3-pod StatefulSet (1 master + 2 replicas) each with a Sentinel sidecar (quorum 2, automatic failover, anti-affinity). It backs two things: the LiteLLM global rate-limit counters and the per-run stop-flags used for fast cancel/budget signalling. Its state is soft and rebuildable — a failover loses at most a fraction of a rate-limit window. (Caveat: the LiteLLM router doesn't speak Sentinel, so per-model caps fall back to per-replica limiting on a master change; acceptable for soft quota protection.)

Model providers

external Behind the gateway sit the actual inference backends. Today that is OpenRouter (fronting many hosted models) via a wildcard passthrough; self-hosted vLLM is a first-class, gateway-fronted source as well (vllm/<model> routes like anything else). A direct, gateway-bypassing vLLM path exists as a deferred option for the day in-cluster inference carries enough load that the proxy becomes the measured bottleneck.

ClickHouse — the analytics projection

eval_engine/analytics.py · deploy/k8s/10-clickhouse-ha.yaml The queryable, ~12B-row store. After each sample completes, the worker flattens it into one row in sample_results. The .eval log stays the immutable artifact in object storage; ClickHouse is the index over it. The engine is the key to exactly-once analytics: 

ENGINE = ReplacingMergeTree(attempt)            -- newest re-execution (higher attempt) wins; dupes collapse
PARTITION BY toYYYYMM(finished_at)              -- monthly: 12-mo TTL is a cheap partition drop
ORDER BY (eval_id, model_id, run_id, sample_id) -- the access-pattern key AND the dedup key
TTL finished_at + INTERVAL 12 MONTH
  • Exactly-once. A re-executed sample re-inserts the same key with a higher attempt; ReplacingMergeTree keeps the newest and collapses duplicates. Headline metrics are computed once at finalize with FINAL over the deduped run partition (never an insert-time materialized view, which would double-count a re-load).
  • Durable async insert. Inserts use async_insert=1, wait_for_async_insert=1 — the server batches concurrent worker inserts into one part (no write amplification) while the call still blocks until durable, preserving the ack-before-flip invariant.
  • HA. When clustered, a 3-replica StatefulSet runs ReplicatedReplacingMergeTree ON CLUSTER with an embedded ClickHouse Keeper raft quorum; reads survive a replica loss via the load-balanced Service.

Why ClickHouse and not Postgres or DuckDB for this: see Storage.

Object store

eval_engine/storage.py · datasets.py S3-API object storage (GCS in this deployment, MinIO/S3 elsewhere) holds the immutable artifacts: Inspect .eval logs, per-sample transcripts (zstd-compressed .json.zst), and content-addressed dataset snapshots. All access goes through a single fsspec wrapper where the URI scheme selects the driver (gcsfs for gs://, s3fs for s3://, a local path in dev) — so the store is swappable with no app-code change, and no native cloud SDK appears in the codebase.

  • Transcript retention is sample-by-default: always keep failures (what you debug) plus a deterministic fraction of passes, with a per-eval opt-in to keep all.
  • Storage tiering — a lifecycle policy cools objects to NEARLINE at 30 days and COLDLINE at 90, since transcript storage is the named dominant cost.
  • Datasets are content-addressed: registration hashes the bytes and writes an immutable snapshot keyed by the hash, pinned on the dataset version for true reproducibility.

Observability — Ops tab & Grafana

eval_engine/ops.py · deploy/k8s/95-grafana.yaml Two complementary views, split by the question they answer:

QuestionIs each subsystem healthy now?How did metrics trend over time?

The Ops tab probes every subsystem concurrently and degrades gracefully (an unreachable backend becomes a down card, never a 500). Its liveness backbone is a heartbeats table the orchestrator and each worker upsert every loop — so the leader-elected singleton and the KEDA-churned workers are observable without coupling to the Kubernetes API (portable to any cloud). It enriches with the in-cluster K8s API (pod phase, restarts, KEDA desired-vs-current) and one-click GCP Log Explorer deep links per component/run.

Grafana provisions everything as code (grafonnet): three datasources (ClickHouse, Postgres, GMP Prometheus) and five dashboards — Quality, Cost & Tokens, Fleet & Orchestration, Model Gateway, and Infra. No Prometheus server to run; it reuses Google Managed Prometheus.

Deployment shape

The whole stack runs on a cost-minimal zonal GKE cluster, provisioned by Terraform (cluster, node pools, GCS bucket, Artifact Registry, reserved IP, IAM, and the KEDA / ingress-nginx / cert-manager Helm releases). Postgres is managed Neon (serverless, external); the one app image is pushed to Artifact Registry and run in four roles.

  • System pool (always-on): API, orchestrator, LiteLLM, ClickHouse, Redis, Grafana, KEDA operator, oauth2-proxy, frontend.
  • Workers pool (spot, 0…N, tainted): the worker Deployment, KEDA-scaled to zero when idle.
  • Sandbox pool (gVisor, autoscale 0…N): per-sample agentic sandboxes.

A fresh cluster is three steps: terraform apply → create secrets → install.sh (renders + applies manifests). Pause/resume scripts scale the system pool to zero overnight. For the detailed resilience posture of this topology, see Resilience & HA.
